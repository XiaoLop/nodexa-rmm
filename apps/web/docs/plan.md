# 待完善

从当前代码和项目路线图来看，项目已经具备比较完整的 Web 管理端骨架，设备、用户、权限、文件、终端、远程桌面等核心能力也已有实现。现在主要不是“页面还没写完”，而是离**可稳定生产发布**还有几类关键缺口。

## P0：发布前必须完成**

1. **认证和会话安全**

目前 Cookie 登录和控制连接已经实现，但还需要补齐：

- MFA、SSO、登录 Token 等认证方式的真实验证。
- 区分认证失败、权限不足、MFA 要求、网关不可用、会话过期。
- Cookie 过期、离线恢复、重复登录和并发登录测试。
- 退出时统一关闭所有控制通道和 Relay 会话。
- 检查日志、错误信息、监控是否可能泄露 Cookie、Token 或认证参数。
- 固定并记录 MeshCentral 目标版本及安全配置基线。
- 配置登录失败限制、账户锁定、HTTPS/WSS 和证书链。

1. **权限门控还没有完全统一**

已经有 `siteadmin`、设备权限和 UI Capability 封装，但部分页面还在使用旧权限字段。

重点需要补：

- 文件面板内部上传、移动、重命名、删除的细粒度权限。
- 远程桌面输入、剪贴板和只读模式权限。
- 页面按钮、路由、侧栏和批量操作统一使用同一套权限模型。
- 服务端拒绝操作后的回读和错误反馈。
- 用户和用户组权限的继承来源、限制权限和最终有效权限展示。

1. **错误处理不完整**

目前控制端和 Relay 都有错误类型，但还没有形成完整、统一的用户体验：

- 登录页仍需避免直接显示底层 `Error.message`。
- 补充授权失败、资源冲突、会话过期等统一错误码。
- 桌面、终端和部分页面仍可能直接拼接底层错误。
- 增加统一重试、重新连接和“执行结果未知”状态。
- Toast 去重和同类错误聚合。
- 增加全局 React Error Boundary 和页面级降级状态。
- 增加前端异常、性能和关键流程监控。

1. **缺少 E2E 和 CI 发布门禁**

仓库已有约 52 个单元、协议和状态测试文件，这是不错的基础；编辑器当前也没有发现静态错误。但没有找到 Playwright 配置，因此浏览器关键流程基本没有自动化覆盖。

至少需要覆盖：

- 登录成功、失败、限流和网关不可用。
- 未登录访问受保护路由。
- Cookie 会话恢复和会话过期。
- 退出后清理连接和状态。
- 不同权限账户的路由、按钮和服务端拒绝行为。
- 设备 CRUD 和批量操作。
- 文件上传、冲突、取消、重试和断线。
- 远程终端、远程桌面的建立、断开和重连。
- 用户、用户组和授权管理。

根级脚本也还没有 `e2e` 命令，见 `package.json`。

## P1：核心功能收尾

1. **设备工作台仍有模拟或推算数据**

需要接入真实数据：

- 网络、硬件、系统和运行时间。
- 标签、指标和事件详情。
- 真实历史在线趋势。
- 分组成员和授权管理。
- 删除设备后的原生事件回读。
- 清除工作台中的模拟数据和推算指标。

1. **远程终端需要真实 Agent 验证**

代码层面已有 xterm 和 Relay 实现，但还需要：

- Windows、Linux、macOS Agent 验证。
- CMD、PowerShell 和默认 Shell 验证。
- resize 行为验证。
- 权限拒绝、超时、断线和有限自动重连。
- 移动端辅助键与触控输入。
- 会话开始、结束和失败审计。

1. **远程桌面需要协议验收**

仍需要验证：

- 鼠标、滚轮负值、扩展键和组合键。
- Unicode、输入法和失焦按键释放。
- 远端剪贴板为空、权限拒绝和写入确认。
- 不同 Agent 的画质参数。
- 多显示器选择。
- 有限自动重连。
- 只读、控制权限和录制状态。

退出码、标准错误流和远端取消等能力，还受 MeshCentral/Agent 协议支持限制。

1. **文件管理缺少传输可靠性功能**

虽然基本文件操作已经实现，但还缺：

- 上传冲突策略：覆盖、跳过、自动重命名。
- 失败任务重试和明确最终状态。
- 传输历史、失败原因和审计。
- 大文件、零字节、特殊字符和深层目录测试。
- 页面刷新、断线、取消和重复提交测试。
- 是否支持上传 ID、分块校验和断点续传的协议验证。

在 Agent 协议确认之前，不能只在前端模拟断点续传。

1. **命令执行需要完善批量能力**

主要包括：

- 批量目标过滤。
- 并发数量控制。
- 失败项保留。
- 结果导出。
- 模板和历史记录的安全存储、脱敏与审计。
- 危险命令的权限和 MeshCentral 事件验证。

仪表盘目前需要从“展示页面”升级成真实数据面板：

- 使用完整历史事件，而不是当前数量或有限样本推算。
- 支持 24 小时、7 天、30 天。

## 审计和历史数据是一个关键缺口

需要统一 MeshCentral 账户事件、设备事件、Relay 日志和 Agent 日志，形成包含以下字段的结构：

- 操作者。
- 动作。
- 目标。
- 成功、失败或结果未知。
- 数据来源。
- 请求 ID、Relay 会话 ID、本地操作 ID。
- 脱敏后的元数据。

不过，没有独立后端和数据库时，下列能力无法由浏览器可靠提供：

- 不可抵赖审计。
- 长期日志归档。
- 浏览器关闭后持续执行的告警规则。
- Webhook 重试。
- 跨浏览器通知未读状态。
- 离线期间可靠通知。

这些应该明确标记为架构限制，或者后续引入服务端持久化。

## 建议迭代顺序

1. 先完成认证、会话、统一错误和生产安全配置。
2. 统一权限门控，并验证高风险操作由 MeshCentral 最终拒绝或授权。
3. 引入 Playwright，建立登录、权限、设备、文件和远程会话 E2E。
4. 清除设备工作台模拟数据，完成文件冲突和重试。
5. 在真实 Windows/Linux/macOS Agent 上验证终端和桌面协议。
6. 完成审计事件归一化和审计页面。
7. 补齐 Dockerfile、配置生成器和生产部署流程。
8. 最后再推进告警、通知、全局搜索、MFA/SSO、系统设置和移动端。

简要说，当前项目已经过了“搭架子”的阶段，但还没有达到“可放心上线”的阶段。最优先的工作不是继续增加新页面，而是把**认证安全、权限、错误语义、E2E、真实 Agent 验证和部署闭环**做扎实。
