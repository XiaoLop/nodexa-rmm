# 实时事件功能实施计划

## 1. 目标

基于 `docs/05-events.md` 中已经确认的 MeshCentral `action: "events"` 历史查询能力，实现一个范围明确、状态相互隔离的实时事件功能：

1. 仪表盘展示内存中最新 30 条实时事件，列表可滚动并随网关推送更新。
2. 用户每次进入实时事件页面时，重新请求最近 60 条历史事件。
3. 实时事件页面支持按事件类型筛选，以及选择历史事件获取条数。
4. 历史事件加载完成后，继续接收并展示当前 WebSocket 连接推送的实时事件。
5. 仪表盘和实时事件页面不共享筛选、获取条数、加载和错误等页面状态。
6. 合并历史事件与实时事件时使用稳定事件 ID 去重，并按事件发生时间倒序排列。
7. 支持查看标准化事件详情和经过安全处理的原始事件数据。

## 2. 本期不实现

- 不按设备分组、用户或时间范围筛选。
- 不提供关键字搜索。
- 不提供手动刷新按钮；重新进入页面即重新获取历史事件。
- 不实现传统页码分页。
- 不导出 CSV 或 JSON。
- 不在共享网关状态中保存实时事件页面的历史查询结果和筛选条件。
- 不依赖 MeshCentral 原生接口完成复杂时间范围或全文查询。

## 3. 页面效果

### 3.1 仪表盘实时日志

- 保留仪表盘现有“实时事件”卡片。
- 从共享网关内存事件中读取最新 30 条数据。
- 卡片内容区域设置固定最大高度和纵向滚动条。
- 新事件到达后自动出现在列表顶部。
- 不受实时事件页面的事件类型和获取条数设置影响。
- 点击“查看全部”进入 `/monitoring/realtime`。
- 没有事件时显示“等待实时事件”。

### 3.2 实时事件页面

页面顶部提供精简工具栏：

- 连接状态：已连接、连接中、重连中或已断开。
- 事件类型：全部、Agent 日志、中继日志、手动操作、命令执行、批量上传、设备变更和设备删除。
- 获取条数：建议提供 30、60、100、200，默认 60。

页面主体使用事件表格，建议显示以下列：

| 列 | 内容 |
| --- | --- |
| 时间 | 使用事件发生时间并转换为本地时间 |
| 类型 | 本地化后的事件类型名称 |
| 设备 | 根据 `deviceId` 解析设备名称，无法解析时显示设备 ID 或“系统事件” |
| 用户 | 优先显示事件中的用户名 |
| 来源 IP | 显示 `remoteaddr` 或标准化后的 `ip` |
| 事件内容 | 显示本地化消息或原始 `msg` |
| 操作 | 打开事件详情抽屉 |

事件详情抽屉包含：

- 标准化事件字段。
- 事件关联设备和用户。
- `relaylog` 的协议、上下行流量等扩展字段。
- `agentlog` 的消息 ID、消息参数、来源地址和会话 ID 等扩展字段。
- 脱敏后的原始 JSON。

## 4. 状态隔离设计

### 4.1 共享状态只保存实时流

`packages/shared-state` 继续负责：

- 网关连接状态。
- 设备和分组快照。
- WebSocket 推送的实时事件缓冲区。

共享事件缓冲区至少保留最新 100 条，以满足仪表盘展示 30 条数据。仪表盘只执行 `events.slice(0, 30)`，不得写入筛选结果或替换共享事件数组。

### 4.2 页面本地状态保存历史查询

实时事件页面在组件内部维护：

- `historyEvents`：最近一次历史查询结果。
- `eventFilter`：当前事件类型。
- `historyLimit`：当前获取条数，默认 60。
- `loading`：历史查询加载状态。
- `queryError`：历史查询错误。
- `selectedEvent`：当前查看详情的事件。

这些状态不得写入共享 store。实时事件仍从共享 store 订阅，并在渲染前与 `historyEvents` 合并。因此：

- 页面改变筛选条件不会清空或修改仪表盘事件。
- 页面改变获取条数不会改变共享实时事件缓冲区大小。
- 页面查询失败不会覆盖网关全局连接错误。
- 离开页面后页面查询状态自动销毁；再次进入时重新加载历史事件。

## 5. 历史事件请求规则

进入页面后使用默认参数发送：

```json
{
  "action": "events",
  "limit": 60
}
```

选择事件类型后发送：

```json
{
  "action": "events",
  "filter": "relaylog",
  "limit": 60
}
```

用户更改事件类型或获取条数时立即重新查询。为避免旧请求覆盖新请求，需要使用请求序号、取消标记或等效机制，只接受最后一次查询结果。

页面重新挂载时必须重新查询，不能直接把上一次页面查询结果当作当前历史数据。

## 6. 控制客户端改造

### 6.1 查询类型

在 `packages/control-client/src/types.ts` 中增加历史事件过滤类型：

```ts
export type HistoricalEventFilter =
  | 'agentlog'
  | 'relaylog'
  | 'manual'
  | 'runcommands'
  | 'batchupload'
  | 'changenode'
  | 'removenode';

export interface EventListOptions {
  limit?: number;
  filter?: HistoricalEventFilter;
}
```

本期页面只需要 `limit` 和 `filter`。现有 `listByDevice()`、`listByUser()` 可保留兼容，但不作为本期页面筛选入口。

### 6.2 请求构造

扩展 `EventsResource.list()`，将有效的 `limit` 和 `filter` 传给 `action: "events"` 请求。对条数进行正整数校验，并限制在页面允许的范围内。

补充单元测试，验证：

- 默认请求使用 100 或调用方指定的默认值。
- `limit` 能正确传入。
- `filter` 能正确传入。
- 无效条数不会发送请求。

## 7. 稳定事件 ID 与去重

当前标准化逻辑在事件没有服务端 ID 时使用接收时间和随机数生成 ID，这会导致同一事件分别通过历史查询和实时推送到达时无法去重。

调整为：

1. 优先使用服务端事件 ID。
2. 没有 ID 时，基于以下字段生成稳定指纹：
   - `action`
   - `nodeid`
   - `userid`
   - `time`
   - `msgid`
   - `msgArgs`
3. 对规范化后的字段序列生成稳定哈希或稳定字符串 ID。
4. 历史事件与实时事件必须复用同一个 `normalizeEvent()`。

页面合并规则：

1. 先将历史事件放入以事件 ID 为键的映射。
2. 再放入实时事件；ID 相同时由实时事件覆盖历史记录。
3. 按 `occurredAt` 从新到旧排序。
4. 当页面设置了事件类型时，历史请求使用服务端 `filter`，实时事件在客户端按相应类型继续过滤。

需要补充测试：

- 同一原始事件多次标准化得到相同 ID。
- 历史事件与实时事件能够正确去重。
- 不同时间或不同设备的相似事件不会被错误合并。

## 8. Web 实现步骤

### 8.1 仪表盘

修改仪表盘事件卡片：

- 从展示 6 条调整为展示最新 30 条。
- 给事件列表增加最大高度和 `overflow-y: auto`。
- 保留现有事件颜色、设备名称解析和本地化消息格式。
- 确保组件只读取共享实时事件，不读取实时事件页面状态。

### 8.2 实时事件页面

新增 `RealtimeEventsPage`：

1. 从 `GatewayProvider` 获取 `GatewayClient`。
2. 从共享 store 订阅实时事件、设备列表和连接状态。
3. 页面挂载后调用 `client.events.list({ limit: 60 })`。
4. 筛选类型或获取条数变化后重新查询历史事件。
5. 使用 `useMemo` 合并、去重、过滤和排序历史事件与实时事件。
6. 提供加载、空数据、查询错误和连接断开状态。
7. 点击事件行打开详情抽屉。

如果客户端尚未连接完成，页面应等待 `client` 和连接状态可用后再查询；连接恢复后可重新拉取当前条件下的历史事件，补齐断线期间可能遗漏的数据。

### 8.3 路由

- 将 `/monitoring/realtime` 映射到 `RealtimeEventsPage`。
- 保留其他 `/monitoring/*` 路由使用现有占位页面。
- 仪表盘“查看全部”继续跳转到 `/monitoring/realtime`。

### 8.4 样式与响应式

- 使用现有控制台卡片、表格、标签和按钮样式。
- 桌面端表格完整显示主要字段。
- 窄屏下允许表格横向滚动，不能压缩到无法阅读。
- 仪表盘事件列表只在卡片内部滚动，不能撑高整个仪表盘布局。

## 9. 错误与连接状态

- 历史查询加载时显示表格加载状态。
- 历史查询失败时保留当前实时事件并显示可读错误，不清空共享实时事件。
- WebSocket 断开时保留已经加载的数据，并提示“实时连接已断开，当前内容可能不是最新数据”。
- WebSocket 重连后继续接收实时事件，并重新查询当前条件下的历史事件。
- 快速切换筛选或条数时，过期请求结果不得覆盖最新结果。

## 10. 测试计划

### 控制客户端

- `EventsResource` 的 `limit` 与 `filter` 请求测试。
- 无效查询参数校验测试。
- 稳定事件 ID 测试。
- 历史与实时事件去重测试。

### 共享状态

- 连续追加事件后仅保留配置的最大数量。
- 新事件保持最新在前。
- 实时事件页面操作不修改共享事件列表。

### Web 页面

- 仪表盘最多渲染最新 30 条事件。
- 仪表盘列表可滚动且实时追加。
- 每次进入实时事件页面都会请求默认 60 条历史事件。
- 改变事件类型会使用正确的 `filter` 重新查询。
- 改变获取条数会使用正确的 `limit` 重新查询。
- 历史事件和实时事件按稳定 ID 去重。
- 页面筛选不会影响仪表盘事件列表。
- 断线、加载失败和空数据状态正确展示。

## 11. 验收标准

- 仪表盘实时事件卡片可查看最新 30 条事件，卡片高度稳定且可以滚动。
- 新事件到达后，仪表盘与实时事件页面都能自动显示。
- 每次进入实时事件页面都会重新请求最近 60 条历史事件。
- 用户可以选择事件类型和获取条数，查询参数与文档中的 `events` 协议一致。
- 实时事件页面的筛选和查询状态不会改变仪表盘内容。
- 同一事件通过历史查询和实时推送到达时只显示一条。
- 用户可以查看事件详情和脱敏后的原始数据。
- `/monitoring/realtime` 不再显示占位页面。
- 相关测试通过，并通过 `pnpm lint`、`pnpm typecheck`、`pnpm test`、`pnpm build` 和 `pnpm format:check`。
