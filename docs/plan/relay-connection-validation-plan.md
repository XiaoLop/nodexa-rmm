# MeshRelay 中继连接验证计划

## 1. 目标

在实现文件管理、远程终端和远程桌面协议前，先使用真实 MeshCentral 环境验证 `@meshcentral/relay` 的公共中继连接流程。

本阶段只验证：

- 控制通道能够获取中继认证信息。
- 控制通道能够通知指定设备建立中继。
- 浏览器能够连接 `meshrelay.ashx`。
- 能够识别真实握手消息并进入 `ready` 状态。
- 会话能够正常关闭，并能正确报告超时、取消和异常断开。

本阶段不实现文件上传、终端交互、桌面画面解析或正式产品 UI。

## 2. 验证范围

首轮使用一台在线设备验证文件管理协议 `p=5`。该协议连接验证通过后，再使用相同验证入口检查终端 `p=1` 和桌面 `p=2` 是否采用相同的中继生命周期与握手方式。

需要验证的完整链路：

```text
应用测试入口
  → GatewayClient 控制通道
  → 请求 authcookie
  → 通知目标 Agent 建立 tunnel
  → RelayClient 创建 meshrelay.ashx WebSocket
  → 等待真实握手
  → 进入 ready
  → 收发最小测试消息或保持连接
  → 主动关闭
```

## 3. 任务拆分

### 任务一：准备真实环境配置

- 确认控制 WebSocket 和 `meshrelay.ashx` 属于同一套 MeshCentral 环境。
- 明确中继基础地址、域路径和反向代理路径。
- 选择一台具有文件操作权限的在线设备。
- 确认浏览器可以访问中继地址，并且代理支持 WebSocket Upgrade。
- 禁止在配置、控制台或错误信息中输出完整 `cookie`、`rcookie` 和带 `auth` 参数的 URL。

### 任务二：建立开发验证入口

在 Web 应用中建立仅供开发使用的中继验证入口，职责包括：

- 从当前设备列表选择一台在线设备。
- 选择协议编号，首轮固定使用 `p=5`。
- 调用 `RelayClient.createSession()`。
- 展示中继生命周期状态及耗时。
- 展示经过脱敏处理的原始消息类型、关闭码和错误信息。
- 提供“连接”“关闭”“取消”操作。

该入口只用于协议验证，不作为正式文件管理页面。

### 任务三：验证控制通道

确认以下行为与真实服务一致：

- `authcookie` 请求能够通过现有 `GatewayClient.request()` 完成。
- 响应中能够取得有效的 `cookie` 和 `rcookie`。
- 响应是否存在外层包装，并核对当前解析逻辑是否兼容。
- `msg/type=tunnel` 能被网关转发给 MeshCentral。
- `nodeid`、`usage`、`p`、`id`、`rauth` 和 `responseid` 字段符合服务端要求。
- 用户无权限、设备离线和设备不存在时能得到可识别的结果。

### 任务四：验证中继地址

验证 `buildRelayUrl()` 和 `buildAgentRelayPath()` 在真实部署下生成正确地址：

- `http`、`https`、`ws` 和 `wss` 协议转换正确。
- MeshCentral 根路径和域路径能够正确保留。
- 不会重复追加 `meshrelay.ashx`。
- 查询参数经过正确编码。
- 浏览器侧 URL 与 Agent 侧路径使用同一个 relay ID。
- 反向代理场景下不会错误指向控制 WebSocket 路径。

### 任务五：验证握手过程

记录浏览器 WebSocket 打开后的真实消息序列，确认：

- 第一条消息是否始终为字符串 `c`。
- 不同 MeshCentral 版本或部署配置是否返回其他握手内容。
- Agent 尚未进入中继时，浏览器是否会先收到其他消息。
- `p=5`、`p=1` 和 `p=2` 是否使用相同握手规则。
- 握手完成后是否需要发送协议初始化消息。

根据结果决定默认握手判断是否继续保留，或者改为由协议描述器提供握手策略。

### 任务六：验证生命周期

逐项验证以下状态路径：

```text
idle
  → authorizing
  → notifying
  → connecting
  → handshaking
  → ready
  → closing
  → closed
```

并验证异常路径：

- 认证失败进入 `error`。
- 通知 Agent 失败进入 `error`。
- WebSocket 建连超时进入 `error`。
- 握手超时进入 `error`。
- 握手消息无效进入 `error`。
- `AbortSignal` 可以取消建连。
- `session.cancel()` 可以取消已建立的会话。
- 远端意外断开只触发一次错误与关闭事件。
- `close()` 和 `cancel()` 重复调用不会产生额外异常。

### 任务七：验证最小数据通道

连接进入 `ready` 后，只验证通用传输能力：

- 发送文本消息。
- 发送 JSON 消息。
- 发送一个小型二进制测试数据，前提是所选协议允许且不会产生设备副作用。
- 接收并区分字符串、`ArrayBuffer`、视图类型和 `Blob`。
- 关闭后禁止继续发送数据。

如果无法安全发送协议消息，则本任务只验证入站数据监听和主动关闭，不构造未经确认的业务指令。

### 任务八：补充验证测试

在真实环境结果明确后补充自动化测试：

- 真实认证响应包装格式。
- 实际握手消息及协议差异。
- 认证或通知阶段失败时的状态转换。
- 建连期间关闭和取消。
- 重复关闭、异常断开及事件去重。
- 域路径和反向代理路径下的 URL 生成。

真实环境集成验证保留为手动测试说明，不在常规单元测试中保存凭据或访问生产设备。

## 4. 验证记录

每次手动验证至少记录：

| 项目 | 内容 |
| --- | --- |
| MeshCentral 版本 | 服务端实际版本 |
| 协议 | `p=5`、`p=1` 或 `p=2` |
| 设备状态 | 在线、离线或无权限 |
| 部署路径 | 根路径或域路径 |
| 状态序列 | 实际触发的生命周期状态 |
| 握手内容 | 消息类型及脱敏摘要 |
| 建连耗时 | 从创建会话到 `ready` |
| 关闭结果 | 关闭码、原因及是否正常 |
| 异常结果 | 错误类型、阶段和服务端表现 |

认证 Cookie、中继完整 URL、账号密码和设备敏感信息不得写入验证记录。

## 5. 完成标准

满足以下条件后，视为中继连接验证完成：

- 一台在线设备能够成功建立 `p=5` 中继并进入 `ready`。
- 已确认真实 `authcookie` 响应和 Agent 通知消息结构。
- 已确认真实握手内容，不再依赖未经验证的假设。
- 正常关闭、主动取消、连接超时和握手超时行为符合预期。
- 认证、通知和连接任一阶段失败时都能进入明确的错误状态。
- 中继 URL 在当前部署路径与反向代理下生成正确。
- 验证过程不会泄露认证 Cookie 或敏感中继 URL。
- 自动化测试已覆盖验证过程中发现的协议和生命周期边界。
- 验证结论已明确哪些生命周期规则可以由所有协议复用，哪些必须由具体协议适配器提供。

## 6. 后续工作

中继连接验证完成后，按以下顺序继续：

1. 固化协议描述器和自定义握手策略。
2. 实现文件管理 `p=5` 的目录列表。
3. 实现单设备单文件上传。
4. 实现单设备多文件与多设备并发调度。
5. 接入正式 Web 上传界面。
6. 验证并实现远程终端 `p=1`。
7. 评估远程桌面 `p=2` 的官方模块复用方案。
