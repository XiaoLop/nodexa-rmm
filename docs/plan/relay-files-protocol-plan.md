# MeshRelay 文件管理协议建设计划

## 1. 当前状态

`meshrelay.ashx` 中继连接验证已经通过，已确认控制通道认证、Agent 通知、浏览器 WebSocket 连接、握手和公共生命周期可以正常工作。

下一阶段进入文件管理协议 `p=5` 的建设。该阶段先实现文件协议层和最小文件管理能力，再逐步扩展到上传、批量上传和正式 Web 界面。

## 2. 阶段目标

在 `@meshcentral/relay` 中建立独立的文件管理协议层，使应用不需要直接处理原始 JSON 消息和二进制文件块。

本阶段主要目标：

- 固化通用中继层与文件协议层的边界。
- 定义文件会话、消息、路径、任务和错误模型。
- 首先实现目录读取，验证文件协议的请求与响应。
- 随后实现单设备单文件上传。
- 为多文件和多设备上传保留扩展能力。

暂不实现文件下载、断点续传、离线队列和跨会话自动恢复。

## 3. 分层设计

```text
应用层
  └─ 文件管理页面 / 上传弹窗 / 批量设备选择
       ↓
FilesClient 或 FilesSession
  └─ 文件协议请求、响应、任务状态和进度
       ↓
RelaySession
  └─ 通用文本、JSON、二进制收发和生命周期
       ↓
RelayConnection
  └─ meshrelay.ashx WebSocket
```

职责划分：

- `RelayConnection`：继续只负责底层连接和原始数据传输。
- `RelaySession`：继续提供协议无关的会话接口。
- `FilesSession`：解释 `p=5` 消息，管理文件操作请求和任务状态。
- 应用层：选择设备、文件和目标目录，并展示结果与进度。

文件管理能力不能直接加入通用 `RelaySession`，避免远程终端、桌面和文件协议相互耦合。

## 4. 建议文件结构

```text
packages/relay/src/protocols/files/
  index.ts
  FilesSession.ts
  types.ts
  messages.ts
  path.ts
  operations/
    listDirectory.ts
    uploadFile.ts
  sources/
    types.ts
    browserFile.ts
  testing/
    fixtures.ts
```

分工：

- `FilesSession`：文件会话入口和操作调度。
- `types`：目录项、文件属性、任务状态、进度与选项。
- `messages`：文件协议消息识别、解析和序列化。
- `path`：Windows、Linux 和 macOS 路径处理。
- `operations`：每种文件操作使用独立状态机。
- `sources`：上传数据源抽象及浏览器文件适配。
- `testing`：协议响应样本和模拟数据。

## 5. 任务拆分

### 任务一：记录真实文件协议消息

使用已经通过验证的 `p=5` 会话，观察 MeshCentral 原生文件管理操作产生的真实消息：

- 文件会话进入可用状态后的初始化消息。
- 请求根目录和指定目录的消息结构。
- 目录列表响应结构。
- Windows 盘符与 Unix 根目录的差异。
- 路径不存在、无权限和设备端错误的响应。
- 请求与响应之间用于关联任务的字段。

协议样本必须脱敏，不保存认证 Cookie、用户目录中的敏感名称或完整设备标识。

### 任务二：定义文件协议公共模型

根据真实消息定义：

- `FilesSessionState`：文件会话状态。
- `FileEntry`：文件或目录的归一化信息。
- `FilePath`：目标平台路径表达。
- `FileOperationState`：单次操作的状态。
- `FileOperationError`：路径、权限、设备和协议错误。
- `FileUploadProgress`：已确认字节、总字节和百分比。
- `UploadSource`：与浏览器 `File` 解耦的数据源接口。

公共类型只描述稳定语义，原始 MeshCentral 字段保留在协议解析层。

### 任务三：实现文件消息路由

`FilesSession` 统一监听 `RelaySession` 的入站消息，并负责：

- 区分 JSON 文本、普通文本和二进制消息。
- 识别文件协议 action 和请求标识。
- 将响应分发给对应的文件操作。
- 忽略或上报无法识别的消息。
- 在会话关闭时终止所有未完成操作。
- 防止多个并发操作错误消费同一条消息。

首期可以限制同一文件会话中只执行一个活动操作，待协议验证稳定后再决定是否允许并发请求。

### 任务四：实现目录读取

目录读取作为第一个正式能力，用于验证完整文件协议层：

- 打开一条 `p=5` 文件会话。
- 请求根目录或指定目录。
- 将原始响应转换为统一的 `FileEntry[]`。
- 支持 Windows 盘符和 Unix 路径。
- 处理空目录、路径不存在、权限不足和设备断开。
- 支持超时和主动取消。

该任务完成后，应能通过开发验证入口查看目标设备目录，但暂不建设完整文件管理页面。

### 任务五：设计上传状态机

在开始发送文件前，先根据真实协议固定上传状态：

```text
idle
  → requesting
  → waiting-start
  → reading
  → sending
  → waiting-ack
  → completed
```

异常状态：

```text
cancelled
failed
timed-out
connection-lost
```

需要明确：

- `uploadstart`、`uploadack`、`uploaddone` 和 `uploadcancel` 的真实含义。
- 第一块和最后一块的发送规则。
- 空文件行为。
- 同名文件覆盖行为。
- 推荐分块大小。
- Agent 错误消息结构。
- 进度应按已发送字节还是已确认字节计算。

### 任务六：实现单设备单文件上传

首个上传版本仅支持：

- 一台在线设备。
- 一个本地文件。
- 一个明确的远程目标目录。
- 顺序分块发送。
- 等待 Agent 确认后发送下一块。
- 上传进度回调。
- 主动取消和操作超时。
- 连接异常时明确失败，不自动重传。

核心协议层接收 `UploadSource`，浏览器应用通过适配器将 `File` 转换为上传数据源。

### 任务七：补充测试

单元测试至少覆盖：

- 目录列表消息解析。
- Windows 和 Unix 路径归一化。
- 空目录与异常响应。
- 多条响应的请求路由。
- 上传正常状态序列。
- 每次 `uploadack` 后才发送下一块。
- 文件读取失败、上传取消和操作超时。
- 中继断开时终止未完成任务。
- 重复确认、未知请求标识和乱序消息。
- 上传过程中不将整个文件一次性加载到内存。

真实设备验证继续保留为手动集成测试，不在自动化测试中依赖生产环境。

## 6. Web 端验证入口

在现有中继验证能力旁增加文件协议开发入口，用于：

- 选择一台在线设备。
- 打开 `p=5` 文件会话。
- 输入或选择远程目录。
- 读取并展示目录项。
- 选择一个小型测试文件上传。
- 展示文件级进度、成功或失败结果。
- 主动取消上传并观察状态。

该入口仍属于开发验证工具。目录读取和单文件上传稳定后，再设计正式文件上传弹窗。

## 7. 安全与限制

- 前端设备选择不能代替服务端权限校验。
- 不在日志中记录 Cookie、完整中继 URL 或文件内容。
- 对远程路径和文件名进行规范化，禁止意外路径穿越。
- 首期限制测试文件大小，避免未验证协议处理超大文件。
- 上传任务必须支持取消和超时，页面关闭时明确处理活动会话。
- 中继断开后不自动重放上传，避免重复写入或产生损坏文件。

## 8. 完成标准

本阶段满足以下条件后完成：

- 文件协议层与通用中继层完成解耦。
- 已记录并确认真实目录列表和上传消息结构。
- 可以稳定读取在线设备的目录并归一化展示。
- 可以向单台在线设备上传一个小型文件。
- 上传过程按确认机制分块发送并报告进度。
- 取消、超时、权限错误和连接中断能够正确结束任务。
- 自动化测试覆盖主要状态和异常路径。
- 开发验证入口可以完成目录读取和单文件上传。

## 9. 后续阶段

完成单设备单文件上传后，再按以下顺序继续：

1. 同一设备会话中顺序上传多个文件。
2. 多设备上传任务调度和并发限制。
3. 批量任务结果汇总、失败重试和取消策略。
4. 接入设备列表的单设备上传按钮。
5. 接入表格选中设备的批量上传入口。
6. 建设正式上传弹窗和进度界面。
7. 分析并实现文件下载、重命名、删除和目录创建。
8. 文件管理稳定后开始远程终端协议计划。
