# 远程桌面协议采集结果

## 1. 文档范围

本文记录 `connection-basic` 场景的一次实际采集结果，用于验证当前客户端通过 Gateway 控制通道和 Relay WebSocket 建立 MeshCentral 远程桌面连接的流程。

本次结果只证明当前测试环境中的实际消息顺序和负载结构。它不代表所有 MeshCentral、Agent、操作系统、显示器配置或录制策略下都具有相同行为。

采集产物位于：

```text
test/captures/desktop/connection-basic/
  manifest.json
  messages.jsonl
  actions.jsonl
  closes.jsonl
  payloads/
    000020.bin ... 000030.bin
  screenshots/
```

## 2. 采集结论

本次采集成功完成了以下过程：

1. Gateway WebSocket 认证成功。
2. 查询设备列表并确认目标设备可用。
3. 通过 `authcookie` 获得浏览器 Relay cookie 和 Agent Relay cookie。
4. 发送 `action=msg`、`type=tunnel`、`usage=2` 的桌面 tunnel 请求。
5. 收到 tunnel 路由结果 `OK`。
6. Relay WebSocket 收到文本握手 `c`。
7. 浏览器发送文本协议号 `"2"`。
8. 收到桌面 metadata、屏幕尺寸、显示器信息和状态命令。
9. 收到一个 jumbo 外包的 JPEG 图块，该图块覆盖完整桌面。
10. 客户端使用 WebSocket close code `1000` 正常结束 Relay 和 Gateway 连接。

`manifest.json` 最终状态为：

```json
{
  "relayHandshake": "c",
  "relayRecorded": false,
  "screenSize": {
    "width": 1920,
    "height": 1200
  },
  "tileCount": 1,
  "lastTile": {
    "x": 0,
    "y": 0,
    "imageFormat": "jpeg"
  },
  "desktopReady": true,
  "screenKnown": true,
  "pendingProtocolBytes": 0
}
```

因此，本次 `connection-basic` 已达到连接基线的主要目标：Relay 路由成功、桌面协议握手成功、屏幕尺寸已知，并形成第一幅完整可见桌面。

## 3. 连接时间线

以下时间均为采集器启动后的单调相对时间，不是跨机器全局时间。

| 相对时间 | 序号 | 方向              | 事件                                     |
| -------: | ---: | ----------------- | ---------------------------------------- |
|  1074 ms |    1 | Browser → Gateway | 发送 Gateway 认证消息                    |
|  1347 ms |    8 | Browser → Gateway | 请求 `authcookie`                        |
|  1591 ms |    9 | Gateway → Browser | 返回 `cookie` 和 `rcookie`，产物中已遮蔽 |
|  1592 ms |   10 | Browser → Gateway | 发送 `type=tunnel`、`usage=2` 请求       |
|  1833 ms |   11 | Gateway → Browser | tunnel 路由返回 `result=OK`              |
|  2543 ms |   12 | Relay → Browser   | 收到 Relay 文本握手 `c`                  |
|  2544 ms |   13 | Browser → Relay   | 发送文本协议号 `"2"`                     |
|  2902 ms |   18 | Relay → Browser   | 收到 `ctrlChannel=102938` metadata       |
|  2969 ms |   20 | Relay → Browser   | 收到命令 `7`，屏幕尺寸变为已知           |
|  4207 ms |   30 | Relay → Browser   | 收到完整首屏 jumbo JPEG 图块             |
| 19549 ms |    - | Browser → Relay   | 发起 code `1000` 正常关闭                |
| 19551 ms |    - | Browser → Gateway | 发起 code `1000` 正常关闭                |

关键耗时：

- tunnel 请求到路由 `OK`：约 `241 ms`。
- 路由 `OK` 到 Relay 握手：约 `710 ms`。
- Relay 握手到屏幕尺寸：约 `426 ms`。
- 屏幕尺寸到完整首屏：约 `1238 ms`。
- Relay 握手到完整首屏：约 `1664 ms`。

本次只发送文本协议号 `"2"` 就收到了完整桌面，没有额外发送刷新命令 `6`、恢复命令 `8` 或编码参数命令 `5`。因此，在当前环境中，建立首屏不需要额外启动探测命令。

## 4. Relay 文本消息

### 4.1 握手

Relay 返回：

```text
c
```

该值说明 Relay 已完成文本握手，并且本次中继未启用会话录制。它不代表首屏已经形成，也不代表远端用户同意状态。

浏览器随后发送：

```text
2
```

该值是桌面 Relay 协议号的文本形式，不是二进制 `u16`。

### 4.2 Metadata

握手后收到一条文本控制消息：

```json
{
  "ctrlChannel": "102938",
  "type": "metadata",
  "users": "<redacted>"
}
```

这确认了桌面连接中存在 `ctrlChannel="102938"` 文本控制通道。用户信息已在共享产物中遮蔽。

## 5. 二进制命令序列

本次 Relay 到浏览器的二进制应用消息序列为：

```text
7, 82, 82, 11, 7, 82, 11, 88, 18, 88, 3
```

所有普通命令均使用大端头：

```text
command: u16
size:    u16
```

解析后没有残留未完成命令，`pendingProtocolBytes=0`。

## 6. 屏幕与显示器信息

命令 `7` 原始字节为：

```text
00 07 00 08 07 80 04 b0
```

按大端解析：

- command：`7`
- size：`8`
- width：`0x0780 = 1920`
- height：`0x04b0 = 1200`

命令 `82` 原始字节为：

```text
00 52 00 0e 00 01 00 00 00 00 07 80 04 b0
```

解析结果：

- display ID：`1`
- X：`0`
- Y：`0`
- width：`1920`
- height：`1200`

屏幕尺寸与显示器几何信息一致，本次环境表现为一个从 `(0,0)` 开始的 `1920 × 1200` 显示区域。

## 7. 完整首屏图块

消息 `30` 对应文件 `payloads/000030.bin`，WebSocket 应用消息总长度为 `190340` 字节。

### 7.1 Jumbo 外包

消息开头为：

```text
00 1b 00 08 00 02 e7 7c
```

解析结果：

- 外层 command：`27`
- 外层 header size：`8`
- 低 24 位内部长度：`0x02e77c = 190332`
- 内部 command：`3`
- 外层总长度：`8 + 190332 = 190340`

外层长度、内部长度和实际文件长度完全一致，没有截断或多余尾部数据。

### 7.2 图块命令

内部命令 `3` 的解析结果：

- X：`0`
- Y：`0`
- 图像格式：JPEG
- 图像数据长度：`190324` 字节
- JPEG SOF 标记：`0xC0`，Baseline DCT
- JPEG 编码尺寸：`1920 × 1216`
- JPEG EOI：位于图像最后两个字节，图像完整

协议报告的桌面尺寸为 `1920 × 1200`，JPEG 高度为 `1216`。JPEG 从 `(0,0)` 开始，宽度覆盖整个桌面，高度覆盖并超过桌面高度。多出的底部 `16` 像素符合图像编码块对齐现象；绘制到 `1920 × 1200` Canvas 时，超出画布的部分会被裁剪。

因此，本次首屏由消息 `30` 中的一个图块完整形成，可以将该消息序号作为本 case 的 `desktop-ready` 边界。

## 8. 完整性与安全检查

已对本次 case 执行采集完整性校验，结果通过：

```text
capture integrity: OK
```

校验内容包括：

- `manifest.json` 的 schema、协议号和 case ID。
- `messages.jsonl` 中消息序号从 `1` 开始连续递增。
- 每条二进制消息均存在对应 `.bin` 文件。
- 每个 payload 的实际长度与 `byteLength` 一致。
- 每个 payload 的 SHA-256 与索引记录一致。
- 文本消息和二进制消息的字段类型正确。
- 所有二进制命令均被完整消费，没有残留字节。

共享文本记录中已经遮蔽：

- Gateway Token。
- Relay `cookie` 和 `rcookie`。
- URL 中的 `auth`、`rauth`、ID 和节点参数。
- 用户名、用户 ID、节点 ID、主机名、IP 和会话 ID等信息。

桌面二进制负载未做内容修改，因为它必须能够用于离线解码和重放。该负载可能包含远端桌面图像，不应提交到公共仓库或发送给无权限人员。

## 9. 已确认的实现依据

本次实际采集可以作为后续桌面客户端实现的以下依据：

1. 桌面 Relay 使用 `protocol=2` 和 tunnel `usage=2`。
2. 当前环境中的最小启动序列为 Relay 握手后发送文本 `"2"`。
3. `c` 表示 Relay 握手完成且未录制，不表示桌面已经 ready。
4. 屏幕尺寸命令 `7` 使用大端 `u16 width` 和 `u16 height`。
5. 显示器几何命令 `82` 在本次单屏环境中携带显示器 ID、坐标和尺寸。
6. 图块命令 `3` 使用大端 X/Y，后续负载为完整图像数据。
7. 大图块可以通过命令 `27` jumbo 外包传输，内部长度使用外包头的低 24 位。
8. 实际图像格式应根据魔数识别；本次首屏为 JPEG。
9. 首屏可能由单个大图块形成，但 ready 判定应基于图块对桌面的实际覆盖，而不是固定认为第一条命令 `3` 就是完整首屏。
10. 文本控制通道 `ctrlChannel="102938"` 在桌面会话中实际出现。

## 10. 尚未确认的内容

本次只完成 `connection-basic`，以下内容仍需独立采集，不能由本次连接结果推断：

- 命令 `88` 和 `18` 的准确业务语义。
- 多显示器列表、切换和全部显示器行为。
- 局部图块更新、窗口移动和旧区域重绘。
- 分辨率变化后的画布清理和新首屏形成过程。
- JPEG 以外的 PNG、WebP 或其他图像编码。
- 鼠标移动、按键、拖动、滚轮和坐标转换。
- 普通键盘、扩展键、Unicode、代理对和 CAD。
- 刷新、暂停、恢复、压缩参数和输入锁。
- 剪贴板读取、写入、空值、并发和权限拒绝。
- `cr` 录制会话、用户同意、仅查看权限和异常断开。
- WebRTC/DataChannel 传输。
- 离屏 Canvas 重放截图与参考截图的像素差异统计。

## 11. 下一步

下一阶段应优先完成画面协议样本：

1. 将消息 `30` 的 JPEG 解码并裁剪到 `1920 × 1200`，生成首屏重放截图。
2. 采集 `screen-small-region`，确认局部更新只覆盖目标矩形。
3. 采集纯色、棋盘格和文字场景，验证颜色、坐标、拼接和清晰度。
4. 采集分辨率变化，确认新的命令 `7` 与后续图块边界。
5. 在画面重放稳定后，再按单动作 case 采集输入协议。

在完成上述样本前，可以开始设计流式命令扫描和 Canvas 顺序绘制结构，但不应将尚未实测的输入与控制字段固化为生产协议 API。
