# 轻量 RMM 功能建设计划

状态：待实施，现有能力待逐项核查。日期：2026-11-03。

## 目标与范围

项目定位为轻量的设备管理工具，以远程控制、批量维护和基础异常提醒为核心。主要使用路径：找到设备 → 查看状态 → 批量处理 → 查看结果。

本次依据用户对“轻量、功能导向，不需要笨重工单系统”的要求，调整原计划的范围与顺序。保留 RMM-001 至 RMM-012 稳定编号，原有完整 RMM 能力按下文收缩或暂缓，不再全部作为建设目标。

首版聚焦脚本库与批量执行、资产查询、基础告警；权限和操作记录随执行能力一起交付。优先级表示开发顺序，不表示功能已经缺失或实现：

| 优先级     | 需求                        | 首期范围                                 |
| ---------- | --------------------------- | ---------------------------------------- |
| P0         | RMM-005                     | 常用脚本、参数、批量执行、逐设备结果     |
| P0 支撑    | RMM-003、RMM-008            | 服务端任务记录、执行状态、权限和审计     |
| P1         | RMM-006                     | 全局软硬件清单、软件版本筛选             |
| P1         | RMM-001                     | 持续离线、磁盘空间不足及恢复提醒         |
| P2         | RMM-009、RMM-007            | Agent 安装便利性、基于已有数据的运维总览 |
| 按需或暂缓 | RMM-002、004、010、011、012 | 具体边界见对应需求，不作为首版前置条件   |

本文是需求与实施计划，不代表功能已经实现或通过真实设备验收。本次仅调整文档，不变更业务代码。Web 为主要交互入口；任务执行、持久化、采集和授权由服务端或 Agent 支撑。

## 现状与架构约束

- 当前已有控制客户端、共享状态及 Relay 实现，Web 接入远程桌面、终端与文件能力。依据：根 README.md、docs/development.md；具体可用范围仍需逐项核查源码与测试。
- 实施前盘点已有设备、权限、事件、资产和任务能力，形成复用与扩展清单，不将本文直接等同于全部缺失。
- 协议与资源 API 放入 control-client，缓存和事件绑定放入 shared-state，远程数据通道放入 relay，Web 负责呈现与交互。
- 浏览器沿用同源 Cookie 会话，服务端负责最终授权；已受理任务不能依赖浏览器持续在线。
- MeshCentral 固定为 1.1.54。新增能力先核实 docs/meshcentral 的版本与协议证据，不假定上游已经提供调度、监控或补丁 API。
- 优先复用已有服务端和存储；新增持久化或执行组件的归属在基线核查后确定，不预先引入通用工作流引擎或独立策略平台。
- 仓库规范引用的 docs/plan/README.md 与 docs/plan/architecture-guardrails.md 当前不存在。沿用本文 tasks 路径，不重建旧计划，也不变更既有阶段编号。

## 需求与验收

### RMM-001：基础监控与提醒（P1）

- 首期：设备持续离线、磁盘空间不足；配置阈值、持续时间及设备或设备组范围，区分正常、异常和数据未知。
- 流程：采集或连接状态变化 → 持续条件判定 → 异常去重 → 通知 → 恢复记录与通知。
- 验收：短暂离线不触发持续离线告警；同一未恢复异常不重复生成告警；过期或采集失败的数据不显示为正常；恢复后保留发生和恢复时间。计划维护可暂停目标规则的通知，并记录操作。
- 通知首期只接入一个实际需要的渠道，渠道待确认；不依赖内置工单。
- 暂缓：CPU、内存、服务等更多规则，复杂规则编排、告警升级、值班与分派体系。
- 依赖：服务端状态采集、规则执行、最小告警记录及通知能力；不以长期性能指标存储为前置条件。

### RMM-002：配置模板与策略（暂缓）

- 当前采用设备或设备组级的少量独立配置；批量任务的目标选择不引入策略继承。
- 出现明确的重复配置需求后，再评估简单模板和批量应用，并能查看设备实际使用的配置。
- 暂缓原范围中的组织继承、例外覆盖、版本发布、冲突计算和策略回滚；不作为监控或任务能力的前置条件。
- 后续验收：配置来源清楚，批量应用逐设备可查，失败不能显示为已应用。继承及冲突规则如需引入，应另行明确。

### RMM-003：最小任务执行底座（P0 支撑）

- 首期：立即执行、服务端保存任务及逐设备执行记录，记录发起人、目标、脚本版本、脱敏参数、时间、状态和输出。
- 流程：服务端授权与校验 → 保存任务及目标快照 → 受控并发执行 → 接收回执 → 保存结果。
- 状态：待执行、运行中、成功、失败、超时、未执行；离线或不支持的目标显示未执行及原因。
- 验收：关闭浏览器后已受理任务继续，重新打开可以查询；部分失败可逐设备追踪；缺少回执不能标为成功；重复提交应防止意外重复创建。运行超时不代表远端进程已终止，应显示结果未知的原因。
- 服务重启后待执行任务可恢复；运行中但无法确认结果的任务保留记录并标明状态，不能自动重放可能产生副作用的操作。
- 暂缓：定时和事件触发、离线待执行、自动重试、任务依赖编排和复杂取消机制。离线设备上线后不自动补执行。
- 依赖：服务端持久化、执行器、Agent 回执和基本并发限制；具体执行和恢复机制先核查现有能力。

### RMM-004：补丁管理（暂缓）

- 暂缓原计划中的跨平台补丁扫描、审批、分批发布、第三方软件补丁目录及合规报表。
- 有明确需求后，先选择一种操作系统，单独定义查询更新、人工触发安装和重启提示的有限范围。
- 普通维护脚本不等同于已实现补丁管理，也不承诺补丁回滚。
- 后续验收：能区分安装结果与待重启状态，明确操作范围及失败原因；平台执行机制和真实设备验证必须先确认。

### RMM-005：脚本库与批量执行（P0，首要功能）

已编写首版实现；2026-11-08 已实测核心单设备链路及部分界面场景，完整验收待补齐，详见 [实测记录](../test/rmm-005-results-2026-11-08.md)。启用方式、真实 Agent 验收及回归场景见 [RMM-005 部署与验收](../test/rmm-005.md)。

第三阶段增加服务端历史搜索、版本历史与对比、版本化标签；同版部署、权限和回退约束见 [RMM 协议](../docs/meshcentral/04-batch-operations.md#rmm-历史搜索与版本扩展)。第三阶段真实环境验收仍待执行，不改变 RMM-005 完整验收状态。

已补充独立持久化设备占用、超时/重启后保留占用、可信迟到回执解除及管理员确认解除。RMM 专属自动化覆盖调度、权限、导入及持久化边界；新版部署后 11 个真实任务已验证核心执行和占用恢复，发现的运行中等待提示问题已本地修复，待重新部署复查。管理员实际解除、权限、五台并发、运维恢复及导入边界仍待完整验收，不据本地模拟标记完成。

本轮范围已扩展为 Windows PowerShell 与 Linux `/bin/sh`。脚本版本明确平台，Linux 支持 `.sh` 导入及按字面值传递参数，两平台复用任务、权限和占用规则。两台 xiao Linux 已实测成功、非零退出、字面参数、输出截断、排队及注销重登；平台编辑后旧任务保留原版本平台。本地兼容 Shell 测试与真实 Agent 结果分别记录。

- 首期：保存常用脚本及版本、参数定义、执行权限；按设备或设备组选择目标，查看逐设备状态、输出和历史。
- 流程：选择脚本 → 输入参数 → 确认目标及操作 → 服务端受理 → 批量执行 → 查看结果并进入设备详情。
- 验收：历史任务能定位实际执行的脚本版本和目标快照；无权限用户不能执行；目标权限由服务端逐设备校验；部分失败不掩盖成功结果；敏感参数不明文进入日志或历史详情。
- 参数和命令拼接方式需明确，防止参数被意外解释为额外命令；执行身份、支持平台和输出截断规则在实现前确定。
- 初期脚本围绕服务检查、诊断采集、临时文件清理等具体维护场景，不承诺一次覆盖所有平台。
- 暂缓：审核工作流、完整软件包仓库、安装检测规则、软件升级和卸载策略。确有软件部署需求后再扩展，不能仅凭安装命令退出成功就声称部署成功。
- 依赖：RMM-003 和 RMM-008 最小范围；不依赖 RMM-002 或完整软件存储平台。

### RMM-006：资产查询（P1）

- 首期：全局软硬件清单，按软件名称及版本筛选设备，显示最近采集时间；筛选结果可进入设备详情或作为批量执行目标。
- 流程：采集 → 标准化 → 查询及筛选 → 选择设备 → 查看或处理。
- 验收：能查询安装指定软件或版本的设备；采集失败、无数据和未安装不能混为一谈；旧数据明确标记；查询和批量目标都遵循设备访问权限。
- 暂缓：完整资产变更时间线、自定义字段平台、保修、采购、折旧和生命周期管理。
- 依赖：已有资产采集能力及必要的查询存储；先核查软件清单在目标操作系统上的可用范围。

### RMM-007：简洁运维总览（P2）

- 范围：基于已有告警与任务数据，展示异常设备、未恢复告警、失败任务和快捷入口，支持授权范围内的筛选和明细跳转。
- 验收：汇总与明细口径一致；无数据、未知和正常明确区分；越权设备不计入统计；可从总览进入具体设备、告警或任务。
- 暂缓：健康评分、长期性能趋势和独立时序存储。总览跟随实际能力建设，不先创建缺乏数据来源的指标。
- 依赖：RMM-001、RMM-003 已产生的数据，不增加独立采集链路。

### RMM-008：权限与操作记录（P0 基础保障）

- 首期：复用原有认证和权限，对批量脚本、重启、删除等敏感操作进行服务端校验，保存可查询的操作记录。
- 记录关联操作者、目标、动作、脚本版本或任务标识、时间及结果，不保存凭据和敏感参数明文。
- 验收：绕过页面仍不能越权操作；设备权限变化后新操作按当前权限校验；操作记录和输出受权限保护，能够从任务追溯发起人及结果。
- 登录恢复、会话吊销等现有能力先核查；发现阻断登录或越权问题优先修复，不因范围收缩而忽略。
- 暂缓：通用审批中心、复杂授权工作流、独立审计分析平台；审计导出按明确需求追加。
- 依赖：现有认证、服务端授权和审计存储；与 RMM-003、RMM-005 同步交付。

### RMM-009：Agent 安装与状态（P2）

- 首期：按平台和分组下载安装包、复制安装命令，查看注册上线状态及 Agent 版本，提供基本失败排查信息。
- 验收：安装材料对应明确平台和目标分组；无权限用户不能生成或获取受限注册材料；界面区分未上线与已上线，不把下载成功当作部署成功。
- 暂缓：大规模远程推送、复杂升级编排、自动清理长期离线设备。后续清理必须预览目标并确认，保留必要操作记录。
- 依赖：上游 Agent 分发、注册及版本查询能力，先核查可复用范围。

### RMM-010：客户／站点管理（暂缓）

- 当前以设备分组满足组织和筛选需求，不建设 MSP 客户模型、客户级策略及报表。
- 只有出现明确的多客户服务需求时再评估，届时需单独设计服务端数据隔离。
- 设备分组不等同于租户隔离，当前计划不承诺多租户能力。

### RMM-011：轻量通知与外部集成（按需）

- 不建设内置工单、责任人分派、工单状态同步或协作流程。
- 为 RMM-001 按实际需要接入一个通知渠道，例如 Webhook 或邮件；具体对象确定后再核实接口。
- 验收：投递失败可诊断；若支持重试，应使用稳定事件标识并限制重试次数；密钥仅在服务端保存，由授权人员管理；通知仅包含接收方所需信息。
- 依赖：RMM-001 及选定的通知接口。通知配置保持独立，不要求先建设通用集成平台。

### RMM-012：安全、备份与网络设备集成（暂缓）

- 不提前建设通用杀毒、加密、备份汇总或 SNMP 网络监控平台。
- 出现明确设备类型、数据源和使用场景后，按单一集成逐项评估采集成本、权限与维护责任。
- 后续验收仍需区分未知、过期、失败和正常，凭据不返回浏览器；状态集成不等于具有备份恢复或安全处置能力。

## 实施阶段与任务映射

以下阶段均待核查与实施，不根据本文直接标记已有功能完成。

| 阶段        | 任务                                        | 交付与退出条件                                                                               |
| ----------- | ------------------------------------------- | -------------------------------------------------------------------------------------------- |
| A：基线核查 | 优先核查 RMM-003、005、008，再核查 006、001 | 列出已支持、部分支持、需扩展及协议证据；确定首批平台、服务端归属与执行边界                   |
| B：批量维护 | RMM-005 + RMM-003、008 最小范围             | 脚本保存、参数、批量执行、逐设备结果和权限记录可用；验证浏览器关闭、服务重启、离线和部分失败 |
| C：资产查询 | RMM-006                                     | 软件版本筛选可用，数据时效可见，查询结果可进入设备或批量任务                                 |
| D：基础告警 | RMM-001 + RMM-011 单一通知渠道              | 持续离线和磁盘空间规则、异常去重、恢复及通知失败诊断可用                                     |
| E：体验补充 | RMM-009、RMM-007                            | 按实际需求补安装便利性及已有数据总览，不扩展为部署或指标平台                                 |

RMM-002、004、010、012 及其他暂缓范围不属于上述阶段的完成条件。后续扩展继续沿用对应编号，先补明确范围与验收，再实施。

各阶段先完成所需服务端或 Agent 能力及资源 API，再完成状态绑定与 Web 页面；复用已有能力时以源码、协议和真实设备验证为准。

## 数据、兼容与回退

- 首期最小持久化对象：脚本及版本、任务和目标快照、逐设备执行记录、操作记录；资产查询和告警阶段再补必要清单、规则及告警记录，不提前建设全部策略和历史指标模型。
- 新增接口保持兼容或版本化。旧 Agent 或不支持的平台应明确显示不可用，不伪造成功结果。
- 任务受理需防止意外重复提交，执行回执需可关联；不将网络超时当作远端未执行，不默认自动重试有副作用的操作。
- 数据迁移在测试环境验证并备份；服务回退保留已产生的任务、执行及操作记录。
- 支持暂停新任务受理或调度；已执行脚本的副作用不承诺自动回滚。输出容量、截断提示和记录保留期在实现前确定。

## 验证与待定事项

实施时按影响包运行 typecheck、lint、test，Web 变更运行 pnpm build:web。真实设备测试与本地测试分开，遵循 docs/development.md 和 test/README.md；验收覆盖离线、重连、浏览器关闭、服务重启、权限拒绝、部分失败和重复提交。

每个需求完成时记录验证命令、结果、平台与未验证条件，再标记完成。本次仅文档调整，不代表上述业务检查已执行。

实现前需确定：首批操作系统与版本、设备规模目标、已有脚本执行和资产采集能力、服务端持久化与执行归属、执行身份、并发和超时边界、敏感参数处理方式、输出及审计保留期、首个通知渠道。

定时任务、完整补丁管理、多租户和工单系统不作为首版待定前置条件；如后续确有需求，再补相应设计与验证范围。
